### User Intent

Obok wybierania języku w task ma byc taki sam selector z tymi samymi stylami, który będzie wybierał tryb egzekucji kodu.
Dane będą pochodzić z API /execution-modes, które zaimplementujesz w controllerze -> a potem w serwisie będzie zwracany enum, który również stworzysz w ramach modelu. Zgodnie z architekturą frontendu
dodasz serwis, potem hook dostepowy, tutaj mozesz dodac jakis cache, poniewaz te dane nie bedą sie zmieniac. Do @GetMapping("/{taskId}") tez możesz dodac jakies cache.
Opcje to RANDOM (Losowe), PLAIN_PROCESS (Proces), DOCKER (Docker). Nastepnie to co uzytkownik wybierze (ma byc przechowywane w TaskContext) jest wysylane do run / submit task.
Request DTO muszą wspierać to pole jako enum i nie moze byc to null. W enumie niech bedzie metoda, ktora dla random po prostu wybeira z wszystkich dostepnych opcji jedną i ją zwraca. To ma byc przekazane do RemoteExecutionRequestDto.
Dodatkowo jako side topic, jezeli uzytkownik klika przeslij, pojawia sie tab "Wynik", to jezeli wynik przyjdzie to ma byc albo ten tab na zielono albo na czerwono, tak samo jak taby z task result.
Kiedy user klika submit, to resetują sie kolory z widocznych testów, a kiedy najpirew kliknie przeslij, dostaje wynik, i potem kliknie uruchom, to ten wynik z przeslij powinien zniknac (caly tab). Ponowne klikniecie przeslij znowu restetuje to co user wyslal w run i znowu najpierw jest bialy tab wynik, a po przyjsciu wyniku czerwony lub zielony.
Kolejny side topic, jak najeżdzam na jakieś pole input / output to nie chce na hoverze zmiany tła. na hoverze może zostać chyba ten szary border, ale powinien byc troche szybszy czas trwania animacji oraz pokazania buttonu copy paste. niech to bedzie ten sam parametr animacji jak button with border.

# Plan Realizacji: OG-162

## 1. Słownik Pojęć i Model Domenowy (Domain Model & Glossary)

- **TaskExecutionMode** (Backend / Frontend):
  Tryb egzekucji kodu wybierany przez użytkownika w widoku zadania.
  Wartości:
  - `RANDOM` („LOSOWE”) – dynamiczny wybór jednej z konkretnych strategii wykonawczych w momencie egzekucji.
  - `PLAIN_PROCESS` („PROCES”) – bezpośrednie uruchomienie procesu na maszynie wykonawczej.
  - `DOCKER` („DOCKER”) – uruchomienie kodu w odizolowanym kontenerze Docker.
- **ExecutionStrategy** (Code Executor Client / RemoteExecution):
  Rzeczywista strategia wykonawcza akceptowana przez mikroserwis wykonawczy (`polymorphia-code-executor`).
  Wartości: `PLAIN_PROCESS`, `DOCKER`.
  Dla trybu `RANDOM`, metoda `resolveStrategy()` mapuje losowo na jedną z powyższych strategii.
- **TaskContext** (Frontend):
  Główny kontekst stanu widoku zadania, przechowujący stan edytora, wybrany język (`language`), wybrany tryb egzekucji (`executionMode`), wyniki lokalnego uruchomienia (`runResults`), status aktywnego zgłoszenia (`submissionStatus`), aktualną zakładkę (`activeTab`) oraz referencje akcji.
- **TaskTab** (Frontend):
  Zakładki w sekcji wyników zadania:
  - `TESTCASES` („testcases”) – widok przypadków testowych.
  - `SUBMISSION_RESULT` („submissionResult”) – widok zgłoszenia („Wynik”).
- **TabOutcome** (Frontend):
  Stan wyniku zakładki wpływyjący na kolorystykę przycisku:
  - `PASSED` (zielony: `bg-primary-success!`)
  - `FAILED` (czerwony: `bg-primary-error!`)
  - `UNKNOWN` (neutralny / biały w stanie zaznaczonym: `bg-secondary-gray!`)

## 2. Architektoniczne Decyzje Projektowe (ADR)

### ADR-1: Rozwiązywanie trybu `RANDOM` przed wywołaniem Remote Clienta

- **Kontekst:** Mikroserwis `polymorphia-code-executor` nie posiada wiedzy o opcji `RANDOM` (zna jedynie `PLAIN_PROCESS` i `DOCKER`).
- **Decyzja:** Metoda `resolveStrategy()` w enumie `TaskExecutionMode` na backendzie dokonuje losowania konkretnej strategii (`PLAIN_PROCESS` lub `DOCKER`) za pomocą `ThreadLocalRandom`. Wartość ta jest przekazywana do pola `strategy` w `RemoteExecutionRequestDto`.
- **Konsekwencje:** Czysty podział odpowiedzialności – system bazowy zarządza preferencjami użytkownika i losowością, a executor otrzymuje konkretną strategię wykonania.

### ADR-2: Zapisywanie wybranego trybu w `TaskSubmission` (Kolejka asynchroniczna)

- **Kontekst:** Zgłoszenia do oceniania (`submitTask`) są przetwarzane asynchronicznie przez poller kolejki (`TaskSubmissionQueuePoller`) i procesor (`TaskSubmissionProcessor`).
- **Decyzja:** Dodanie pola `execution_mode` (not null, bez domyślnej wartości w schemacie) do encji `TaskSubmission` oraz migracji Flyway `V28__add_execution_mode_to_task_submissions.sql`. Podczas pobierania z bazy `TaskSubmissionContext` przenosi tryb egzekucji do `TaskSubmissionExecutionService`.
- **Konsekwencje:** Zgłoszenie zachowuje informację o trybie wybranym przez użytkownika, a worker może wywołać `resolveStrategy()` w trakcie egzekucji test case'ów.

### ADR-3: Dwuwarstwowa Strategia Cachingowa (HTTP Cache-Control + Spring @Cacheable + React Query)

- **Kontekst:** Lista trybów egzekucji oraz szczegóły zadania (`GET /tasks/{taskId}`) są statyczne z perspektywy pojedynczego zadania. Przy 100 użytkownikach otwierających to samo zadanie, pobieranie danych z bazy SQL za każdym razem obciąża serwer i bazę PostgreSQL.
- **Decyzja:**
  1. Frontend (TanStack Query):
     - `useExecutionModes`: `staleTime: 1000 * 60 * 10` (10 minut TTL).
     - `useTaskDetails`: `staleTime: 1000 * 60 * 2` (2 minuty pamięci podręcznej).
  2. Backend HTTP Cache-Control:
     - `GET /tasks/execution-modes`: `CacheControl.maxAge(Duration.ofMinutes(10)).mustRevalidate()`
     - `GET /tasks/{taskId}`: `CacheControl.maxAge(Duration.ofMinutes(2)).cachePrivate()`
  3. Backend In-Memory Server Cache (`@EnableCaching` + `@Cacheable`):
     - Włączenie cache w Spring Boot (`@EnableCaching`).
     - Metoda pobierająca szczegóły zadania zostaje objęta `@Cacheable(value = "taskDetails", key = "#taskId")` w dedykowanym `TaskDetailsService`.
     - **Bezpieczeństwo i autoryzacja:** Sprawdzenie uprawnień `taskAuthorizer.checkTaskAccess(taskId)` jest wykonywane w `TaskController` przed wywołaniem buforowanego `taskDetailsService.getTaskDetails(taskId)`, co gwarantuje, że nieuprawniony student nie otrzyma danych z cache bez weryfikacji dostępu do kursu.
- **Konsekwencje:** Pierwszy użytkownik ładuje zadanie z PostgreSQL do pamięci RAM serwera, kolejnych 99 użytkowników otrzymuje odpowiedź natychmiast z RAM w ułamku milisekundy, a przeglądarka każdego z nich unika zbędnych zapytań sieciowych przez czas trwania TTL.

### ADR-4: Zarządzanie cyklem życia zakładek i wyników (Uruchom vs Prześlij)

- **Kontekst:** Użytkownik oczekuje rozłączności wyników testów uruchomienia (`runTask`) oraz zgłoszenia (`submitTask`).
- **Decyzja:**
  - Kliknięcie **Uruchom** (`handleRunTask`):
    - Resetuje i ukrywa zakładkę „Wynik” (`activeSubmissionId: null`, ukrycie taba `SUBMISSION_RESULT`).
    - Ustawia aktywny tab na `TESTCASES`.
    - Wykonuje `runTask` i aktualizuje wyniki widocznych testów.
  - Kliknięcie **Prześlij** (`handleSubmitTask`):
    - Resetuje stan mutacji `runTask` (czyści wyniki i kolory widocznych testów do stanu neutralnego).
    - Natychmiast aktywuje i wyświetla zakładkę „Wynik” w stanie oczekiwania (biała/neutralna – `TabOutcome.UNKNOWN`).
    - Po nadejściu wyniku zgłoszenia: zielony (`PASSED`) wyłącznie gdy `passedCount === totalCount && status === COMPLETED` (100% testów zaliczonych), w przeciwnym razie czerwony (`FAILED`).

### ADR-5: Standaryzacja animacji i interakcji kontenerów wejścia/wyjścia

- **Kontekst:** Hover na polach wejścia/wyjścia testów nie powinien zmieniać tła, a czas przejścia i pojawiania się ikony kopiowania ma być zgodny z `ButtonWithBorder`.
- **Decyzja:**
  - W `task-test-case/index.css` usunięcie klasy `hover:bg-primary-dark`.
  - Pozostawienie obramowania na hover (`hover:border-secondary-gray/40`).
  - Zastąpienie `duration-500 ease-in-out` globalną klasą `@apply custom-ease-with-duration` (zdefiniowaną w `globals.css` jako `duration-400 ease-[cubic-bezier(0.34,1,0.2,1)]`).
  - Użycie tej samej klasy animacji na przycisku kopiowania `task-test-case-copy-button`.

### ADR-6: Konwencja REST API – Liczba mnoga dla kolekcji zasobów (`/tasks/execution-modes`)

- **Kontekst:** Zgodnie ze standardami projektowania RESTful API (np. Zalando REST Guidelines, Google API Design Guide), kolekcje zasobów powinny być reprezentowane przez rzeczowniki w liczbie mnogiej (`nouns in plural form`).
- **Decyzja:** Endpoint zwracający kolekcję dostępnych trybów wykonania to `GET /tasks/execution-modes`. Liczba pojedyncza jest rezerwowana dla identyfikatorów pojedynczych zasobów lub unikalnych singletonów.
- **Konsekwencje:** Spójność architektury REST API, czytelność oraz zgodność z ogólnoświatowymi standardami inżynierii oprogramowania.

### ADR-7: Reaktywny stan asynchroniczny w TanStack Query (Single Source of Truth)

- **Kontekst:** Stan zgłoszenia (`submissionId`, status przetwarzania, wynik akceptacji) pochodzi z zapytań asynchronicznych (mutacja `submitTask` oraz poller `useTaskStatus`). Duplikowanie tego stanu w lokalnym reducerze React powoduje ryzyko desynchronizacji i zbędny boilerplate (`isSubmissionInitiated`, `activeSubmissionId`).
- **Decyzja:**
  - `TaskState` w reducerze odpowiada wyłącznie za czysty stan UI (`language`, `selectedExecutionMode`, `activeTestCaseIndex`, `activeTab`).
  - Stan zgłoszenia jest czerpany bezpośrednio z TanStack Query: `activeSubmissionId = submitTaskData?.submissionId ?? null`, `hasSubmission = isSubmitTaskPending || activeSubmissionId !== null`.
  - `resetSubmitTask()` i `resetRunTask()` czyszczą stan mutacji TanStack Query, co automatycznie czyści stan wizualny bez konieczności wprowadzania sztucznych flag.
  - Obliczanie `isSubmissionAccepted` jest enkapsulowane w hooku `useTaskStatus`.
- **Konsekwencje:** Brak redundancji stanu, zgodność ze wzorcami TanStack Query, eliminacja możliwych race condition.
